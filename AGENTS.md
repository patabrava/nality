# AGENTS.md

0) Non-negotiable Locality Envelope (default)
- Vanilla-first: prefer platform primitives; default to vanilla first, and only use frameworks if justified.
- Dependency budget: 0 by default; max 1-2 per concern, only if justified.
- File budget: Fewer is better. Create as fewer files as possible to achieve production-grade quality without creating context overwhelm (zero unnecessary files).
- LOC budget: target <= 1000 LOC/file; split when > 2000 LOC. Avoid context rot growth.
- Every Plan offered must explicitly state: {files, LOC/file, deps}.

1) Role routing (global)
- Keep bridgecode playbooks in `bridgecode/` and generated artifacts in `agents/`; do not mix the two folders.
- When doing backend development always follow the LLM_FRIENDLY_ENGINEERING_BACKEND instructions.
- When doing frontend design always follow the LLM_FRIENDLY_ENGINEERING_FRONTEND instructions.
- When planning or debugging always follow the LLM_FRIENDLY_PLAN_TEST_DEBUG instructions.
- Whenever starting a conversation (no previous turns detected) check only one time, to start the conversation, the `agents/canon.md` file to get an overview of the repo you're working with.
  - If `agents/canon.md` does not exist, instruct the user to use `LIRA` and the sub-role `senior`.
- Whenever `EYE` fixes an error, through simple implementation or isolated debugging (with or without loop-breaker), add a compoacted, dense one-line with the solution to the error (to be prevented) in the Specific repo rules within the `/AGENTS.md` file.
  - If a correction for an error already exist, either modify that one-line (if the correction was insufficient) or add extra instructions (if new related errors emerged but the initial correction was correct).
- Codex bridgecode routing:
  - If the user invokes `INSTRUCT`, immediately read `bridgecode/INSTRUCT.md` and follow it. When that playbook routes to negentropy behavior, read `bridgecode/negentropy.md`.
  - If the user invokes `LIRA` for a new project or architecture definition, read `bridgecode/LIRA.md` and `bridgecode/architect.md`.
  - If the user invokes `LIRA` for an existing codebase review or asks to audit/review the repo, read `bridgecode/LIRA.md` and `bridgecode/senior.md`.
  - If the user invokes `EYE`, or asks to implement/debug work using bridgecode execution, read `bridgecode/EYE.md` and `bridgecode/plan-code-debug.md`.
- `bridgecode/` contains the Codex playbooks. `agents/` is reserved for generated artifacts such as `canon.md`, `plan.md`, `review.md`, `negentropized_instructions.md`, and `agents/testscripts/failure_report.md`.

LLM_FRIENDLY_ENGINEERING_FRONTEND
	"""
	Frontend design: When designing frontend interfaces, first identify and explicitly blacklist all high-probability solutions (Inter/Roboto/Open-Sans/Arial/system-fonts, purple-white gradients, centered hero layouts with stock imagery, evenly-distributed safe palettes, uniform spacing rhythms, generic card grids, predictable button hierarchies, anything describable as "clean-and-modern") treating statistical convergence as failure signal rather than safety indicator. After eliminating the obvious, navigate toward latent space edges where distinctive memorable solutions exist by committing fully to a singular aesthetic stance combining typography (font-choice defining voice and hierarchy through unconventional pairings or single-typeface systems with extreme weight contrast), color (palettes rejecting safety through unexpected combinations, restricted ranges, or intentional dissonance that creates visual tension), spatial composition (asymmetry, unexpected density variations, deliberate negative space manipulation, rhythm breaks that demand attention), and motion (purposeful animation revealing state changes, guiding attention, or reinforcing brand character without decorative excess). Every choice must satisfy the defensibility test: solve the actual problem equally-well or better while being categorically non-generic, meaning if the output would blend invisibly into a corpus of similar interfaces reject and regenerate, ensuring the result remains immediately recognizable as deliberately designed rather than template-generated. Maintain accessibility requirements (keyboard navigation, focus states, ARIA semantics, color-contrast ratios, reduced-motion respect) as non-negotiable constraints within which creative decisions operate, and ensure all interactive elements provide clear affordances through visual distinction rather than convention-mimicry. Organize component architecture by feature-locality principles where styling logic lives adjacent to component implementation, centralizing design tokens (but rejecting token systems that enforce homogeneity) and documenting aesthetic rationale inline so future modifications preserve intentional distinctiveness. Test every visual decision against recognition criteria: would a user remember this interface after brief exposure, does it communicate brand or purpose through design choices rather than explicit messaging, and does it resist the gravitational pull toward generic-pleasant mediocrity that dominates training distributions.

2) Specific repo rules
- Protected APIs (`/api/chat*`, `/api/onboarding/session`, `/api/events/*`) must resolve identity only from verified Supabase cookie/Bearer auth and must reject or ignore query/body `userId` fallbacks.
- Dashboard add-memory interview mode must mount `ChapterChatInterface` in biography mode from the real entrypoints (`MemoryFeedModule`, `TimelineModule`, `ChatModule`), seed from `users.alt_onboarding_private`, and never fall back to `OnboardingChatInterface`, onboarding prompts, onboarding-session persistence, or the legacy `/onboarding` chat page.
- Secrets stay server-only: never log Supabase service-role fragments, never return provider API keys to the browser, and keep auth-debug endpoints development-gated and sanitized.
- Default Vitest runs must exclude localhost-dependent `src/__tests__/e2e/**`; keep live-server suites behind explicit manual scripts.
- Admin-only UI and target-user interview writes must be enforced in middleware plus server helpers, and they must never reuse user-scoped `/api/interview-sessions` or `/api/chat/biography` paths for privileged target-user persistence.
- Every workspace package included in root `turbo type-check` must own a real `tsconfig.json` with modern ES libs; empty package tsconfigs silently fall back to ES5 and explode dependency type surfaces.
- Client bootstrap effects that create interview sessions or auto-send the first chat turn must be React StrictMode-safe: cleanup must abort and reset in-flight refs when no session id was committed, otherwise dev remounts will suppress the real biography bootstrap.
- Gemini-backed routes must use a currently supported production model id (`gemini-2.0-flash` or newer supported replacement), never deprecated `*-exp` aliases that return `404` while the UI only shows a generic chat-stream error.
- If a `/_next/static/chunks/app/(protected)/dash/*/page.js` request 404s in `next dev` while the route file exists, treat it as stale or incomplete `.next` dev-manifest state first: restart the active dev server, force a fresh route compile, and only debug the route module if the rebuilt chunk still 404s.
- Guided memory interview must stay a shared biography session with both shells available: launch voice-first from add-memory entrypoints, allow in-modal switch to `ChapterChatInterface`, and never let shell switches create a second interview session or auto-finalize the first one.
- Local admin access depends on app-level env `ADMIN_EMAIL_WHITELIST`; when `/admin` silently falls back to `/dash`, check `apps/web/.env.local`, restart Next so the env reloads, and verify the signed-in Supabase email matches the whitelist exactly.
- Middleware login redirects must derive the incomplete-onboarding target via `getIncompleteOnboardingPath()` (or an equivalent defined constant); never reference an undefined `incompletePath` symbol or `next build` will fail type-check.
- In this app, new protected/product surfaces must not rely on Tailwind utility classes unless Tailwind directives are actually mounted in the runtime CSS pipeline; use shared tokens plus CSS modules or inline styles, otherwise the page ships as near-unstyled HTML.
- With `exactOptionalPropertyTypes` enabled in `apps/web`, route/helper inputs must omit optional fields entirely instead of passing `undefined` through (use conditional object spreads for values like `chapterIds`), or `next build` fails during the type-validation pass.
- When feature catalogs use `as const` literal topic arrays, avoid `.includes(dynamicString)` in production code; use `some(topic => topic === value)` or widen the array first, otherwise Next's full type build can infer `never` and fail only at compile time.
- Chapter planning/readiness must ignore bootstrap/generated placeholder memories like `Bitte eröffne das Biografiegespräch...`; otherwise old session scaffolding inflates readiness and produces fake draft chapters from non-user content.
- Chapter planning context must collapse `interview_question_progress` to the latest row per `question_id` across sessions before readiness/planning; session-history duplicates otherwise inflate answered-question coverage and create premature draft chapters.
- Vitest in `apps/web` must include `src/**/*.test.ts`, not only `src/__tests__/**`; otherwise feature-local vertical-slice tests are silently skipped and the planned EYE testscript paths fail even when the code is correct.
- When mirroring Supabase progress-row updates in local route state, compute counters from the pre-update snapshot; reading a shared mutated object after the DB helper runs can double-increment `asked_count` and corrupt planner state under real code or test doubles.
- With `exactOptionalPropertyTypes` enabled, never pass `headers: undefined` or similar optional fetch/init fields explicitly; build the `RequestInit` object conditionally or Next/TS builds will fail on otherwise-valid client fetches.
- For tuple-based catalog metadata unions, never access optional keys directly off the raw tuple tail; normalize with `'key' in options` guards first or Next/TS will reject narrow variants during production builds.
- Seed-row factories that feed tests or planner state must return the widened contract type, not a literal-object inference; otherwise fields like `answer_excerpt` get trapped as `null` and TypeScript blocks legitimate state transitions in tests and runtime helpers.
- Client data-loading effects in protected/admin views must treat `AbortController` cleanup as expected control flow, guard state updates with a local cancelled flag, and never surface abort messages like `signal is aborted without reason` as user-facing errors.
- Biography interview entrypoints must open `BiographyInterviewModal` for both voice and text paths; voice mode must append `BIOGRAPHY_INTERVIEW_START_TOKEN` before listening, and modal session-creation effects need an in-flight ref plus abort cleanup so auth hydration/StrictMode cannot create duplicate interview sessions.
- Biography interview reopen must resume the latest unfinished session and closing the modal must pause rather than PATCH it to `complete`; otherwise every reopen starts a fresh session and re-asks `basis.birth`.
- App Router route handlers that repo tests invoke directly should keep the `Request` parameter in the exported signature even when unused; zero-arg `GET/POST` handlers type-check poorly against the existing route-test call pattern.
- Biography generation/export routes must follow the shared provider-selection pattern and fall back to Gemini (`GEMINI_API_KEY` or `GOOGLE_GENERATIVE_AI_API_KEY`) when OpenAI is absent; hardcoded OpenAI-only generation breaks this repo's local and live dashboard flow.
- User-facing PDF export must use a standards-compliant generator like `pdf-lib` and return `Buffer.from(pdfBytes)` from the route; handwritten PDF byte assembly can parse loosely yet still open as a damaged file in macOS viewers.
- Biography interview answers that reveal birth/profile traits must sync `users.birth_*` and `user_profile` directly from `/api/chat/biography`, with lightweight backfill from answered progress rows when those fields are still empty; otherwise memories/chapters advance while `/dash/profile` stays blank.
- Server-side chapter-chat extraction callbacks must build internal fetch URLs from `req.url` rather than `NEXT_PUBLIC_APP_URL`; public app-url env drift otherwise makes `[SAVE_MEMORY]` extraction silently stop working in local or misconfigured environments.
- Biography voice-agent bootstrap must attempt the Deepgram temp-token grant before any greeting/context generation; standard Deepgram keys can 403 on `/v1/auth/grant`, and that path must degrade to the legacy server-side voice loop instead of surfacing a 500.
- Biography voice auto-start must be idempotent per `interviewSessionId`; React StrictMode/dev remounts can otherwise trigger a second bootstrap that immediately aborts listening before any transcript is emitted, making the interview appear deaf.
- Legacy biography voice must stop Web Speech recognition and clear `isListeningRef` before `onUtteranceEnd`, and it must use a sub-1s silence timeout; otherwise recognition restarts during assistant thinking, creates dead air, and can abort the next TTS turn.
- Biography voice remount guards must persist per-session state on `globalThis`/browser-global storage, including the chosen transport and last spoken assistant message id; a remounted `interviewSessionId` must resume listening without replaying old assistant audio or surfacing `__START_BIOGRAPHY_INTERVIEW__`, or Fast Refresh/remounts will reboot the conversation and make STT appear broken.
